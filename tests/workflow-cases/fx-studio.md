# FX Studio continuation protocol

Use the `fx-scene-*` cases in [cases.json](cases.json) for a fresh host run. This protocol is anonymized: choose an authorized private account and visual brief at run time; do not place customer names, media, source code, handles, screenshots or private URLs in tracked fixtures. Record observed identities and media only in the approved private acceptance record. Local fixture checks show that the cases are structured, not that a host installed or used the skill.

## One-scene creative continuation

Start with a brief that needs visible motion, depth and typography. Allow the agent to open FX Studio, read the live scene-authoring contract and make a first saved scene. Give ordinary feedback such as “make the movement bolder and the lettering more distinctive” without timestamps, code, tool names or repair hints. It should continue the same scene, not create a second effect or edit a Clip. Record the current scene ID, revision and source SHA after each accepted write; match preview revision/source/snapshot identity to the source actually reviewed. Inspect multiple moments and play/seek backward. Still PNGs alone cannot establish motion quality.

Score the first and revised result on whether the requested idea is legible, the direction noticeably improved, motion is intentional and seekable, typography remains readable, and the open view reflects the current revision. A correct tool sequence with weak creative output is partial at best. Distinguish an app view the reviewer actually saw from a returned `studio_url`.

## Controlled failures

For the stale branch, advance the source from a separate authorized writer after the agent's read. The agent should re-read, reconcile the other change and continue on the same scene with current guards. For the runtime branch, use a syntactically valid candidate known to fail on mount or a later frame. A saved receipt is not a successful preview: observe the runtime error, the prior last-good display, and a later repaired revision with a matching new preview. Do not require deliberately unsafe network access to trigger the test.

For discovery, begin with a session whose FX tool catalog is missing or stale. Observe whether the agent refreshes/reconnects the existing connector and starts a new conversation where required, or stops accurately. Do not equate source files, a generic MCP connection, a settings-page catalog, or a local validator with skill invocation in the tested host.

## Scope and application

Run source-only and application requests separately. Source-only must not write Project/account defaults, Episode/Clip state or a Render. For a new one-Clip request, check source-backed Clip selection, then whether the host exposes the documented template insertion and exact-occurrence replacement capability. Observe the provisional FX occurrence being replaced by the saved-scene recipe on the same Clip, its changed duration, and an exact Export only if rendering was requested. If the host lacks the route or read capability, the safe result is a saved scene plus an honest boundary—not a Project-default change or an invented recipe. A Project Signature-default request is a different case and must be evaluated with its own authorization and frozen-result proof.

Use the shared [record template](record-template.json) for host, package, connection and outcome evidence. Mark unobserved audio, motion, publication and Export fields as unobserved; standalone FX preview is silent and is not an Export.
